# CROWNSCAR — правила автономной разработки

## Цель

Развивать CROWNSCAR как интересную стратегию, которая создаёт истории и заставляет игрока принимать понятные, трудные решения. Не добавлять системы, кнопки и показатели без ясной пользы для игрового процесса.

## Источники задач

Перед началом работы прочитать:

1. `KINGDOOM_DESIGN.md` — направление игры и ограничения дизайна.
2. `ROADMAP.md` — порядок задач и критерии готовности.
3. `DEVLOG.md` — что уже сделано, проверено или сломано.

Если этих файлов ещё нет, не придумывать крупную механику самостоятельно. Сначала создать или уточнить их вместе с владельцем проекта.

## Безопасный рабочий цикл

1. Выбрать одну небольшую незавершённую задачу из `ROADMAP.md`.
2. Проверить текущее поведение и связанные сцены и скрипты.
3. Внести минимальные изменения, необходимые для задачи.
4. Запустить автоматическую проверку проекта в Godot 4.7.1.
5. Если проверка не прошла — исправить ошибки до продолжения.
6. Кратко записать результат и проверки в `DEVLOG.md`.
7. Сделать отдельный понятный Git-коммит только после успешной проверки.

## Обязательные проверки

- Основная версия движка: Godot 4.7.1.
- Проект должен открываться без ошибок разбора GDScript и отсутствующих ресурсов.
- По возможности запускать проект без окна с ограничением времени, чтобы выявлять ошибки запуска.
- Для новой игровой логики добавлять воспроизводимую проверку или тест.
- Не объявлять задачу готовой, если проверку невозможно было запустить; явно записать причину в `DEVLOG.md`.

## Ограничения

- Не удалять сцены, сохранения или крупные подсистемы без отдельного решения владельца.
- Не переписывать несвязанные части проекта в рамках одной задачи.
- Не менять формат сохранений без миграции или явного разрешения владельца.
- Не публиковать секреты, локальные сохранения, кэш Godot и экспортированные сборки.
- Не выполнять принудительную отправку Git и не переписывать опубликованную историю без явного разрешения владельца.
- Не объединять несколько крупных механик в один коммит.

## Приоритет качества

При конфликте приоритетов использовать порядок:

1. Проект запускается и не повреждает данные игрока.
2. Игровое решение понятно и интересно.
3. Интерфейс сообщает последствия действий.
4. Код остаётся простым и проверяемым.
5. Визуальная полировка выполняется после работоспособности механики.

## Когда остановиться и спросить владельца

- Задача требует изменить основную идею игры.
- Есть несколько несовместимых вариантов, сильно влияющих на игровой процесс.
- Нужны удаление данных, переписывание истории Git или публикация новой версии.
- Не удаётся пройти одну и ту же проверку после разумных попыток исправления.
